# Evaluation harness

Two experiments. Each is one command that measures every system it names in one run and ends with one
figure of the paper and the data it plots:

| Experiment | Figure | Question |
| --- | --- | --- |
| `experiments/northbound.yaml` | `acked-vs-payload-influxdb-all` | Device → sink: latency until the sink acknowledged the write, against payload size, for the **DMP** of this repository, **Eclipse BaSyx DataBridge** (the system it replaces), **nodered-dmp** (RWTH IAT) and the **PATCH reference** (the repository write alone); the DMP also into an InfluxDB 2 TimeSeries segment |
| `experiments/southbound.yaml` | `southbound-components` | AAS → device: a Property write or an Operation call through BaSyx and the DMP, split into the device interface, the DMP and BaSyx, against the device's **native interface** |

Every result folder names the exact scripts, images and versions that produced it.

## Equal grounds

aas-property, the one scenario every system runs, uses only what IDTA AIMC 2.0 and AID 1.2 define (no Response*,
no Evaluation, none of aas-model's AID extension terms). influxdb-segment (the InfluxDB target) and invoke-* (the
Operation's response mapping) use DMP extensions and run on the DMP only. Each system gets the
scenario in the form it accepts; every adaptation is recorded in the run's manifest
(`systemsUnderTest.<system>.adaptations`):

| System | Runs | Adaptations |
| --- | --- | --- |
| `dmp` | every scenario | none: reads the scenario's AIMC and AID |
| `databridge` | aas-property | reads no AIMC: its own config files, written from the scenario; a JSONata transformer picks the member and encodes it as a JSON string (its AAS sink quotes without escaping); per-message logging at WARN |
| `nodered-dmp` | aas-property | its generator parses AIMC 1.0 only: the mapping is rendered as AIMC 1.0, the member's reference as its property; it reads no Transformation and no schema: the member extraction is written in JavaScript into the generated function node |
| `patch` | aas-property | not a system: the load generator PATCHes each message's value itself (`tools/loadgen.py --target patch`) |
| `native` | write-*, invoke-* | not a system: the client writes to or calls the device itself, with the same bytes, QoS and device |

## Requirements

- Docker with Compose v2 (the testbed, the measurement tools, the DMP build)
- [uv](https://docs.astral.sh/uv/) (`uv.lock` pins every dependency)
- About 4 GB of free memory, no other stack running, the CPU governor at `performance`

Everything runs from this directory:

| Folder | Holds |
| --- | --- |
| `experiments/` | the two experiments' parameters (YAML) |
| `harness/` | the runner (`run.py`), one point's lifecycle (`point.py`), the testbed and tool containers (`testbed.py`) |
| `adapters/` | one module per system under test: how it takes a scenario, how it is deployed and when it is ready |
| `tools/` | the measurement tools, run in the harness image: load generator, Operation caller, device simulator, event observers, residence from the capture |
| `analysis/` | raw samples → `summary.json` (`summarize.py`), `summary.json` → the figure and its data (`figures.py`) |
| `test_aas/` | the scenarios' AAS environments (one JSON file each, loadable into BaSyx), generated by `../fixtures/scenarios.py` with aas-model |
| `testbed/` | the Compose project, the broker's configuration, the nodered-dmp flow generator's image |
| `results/` | one folder per run, not versioned |

## Run

```bash
uv run python -m harness.run experiments/northbound.yaml   # ~2.5 h: dmp, databridge, nodered-dmp, patch
uv run python -m harness.run experiments/southbound.yaml   # ~40 min: dmp, native
```

Each writes `results/<experiment>/<UTC time>/`, ending with the figure (`.pdf`, `.png`) and its data
(`.csv`), made from that run alone. `uv run python -m analysis.figures results/<experiment>/<run>`
redraws them.

- `--dry-run` prints the points and the expected duration.
- `--resume results/<experiment>/<run>` completes an interrupted run (failed points are repeated), then
  draws the figure.
- `--dmp-image <image>` measures a prebuilt DMP image. Without it, the runner builds
  `dmp:eval-<commit>` from this repository, `-dirty` if it has uncommitted changes.
- `--require-quiet-host` refuses to start while other containers run; without it they are only listed
  in the manifest.
- `SUT_CPUSET` / `INFRA_CPUSET` / `TOOLS_CPUSET` (default `0-3` / `4-7` / `8-15`) pin the system under
  test, the infrastructure and the measurement tools to cores of their own (on a hybrid CPU, put the
  first two on performance cores). `SUT_CPUS` / `SUT_MEMORY` (default `2` / `2g`) limit every system
  under test; `--jvm-heap` (default `1g`) is the `-Xmx` of the DMP and DataBridge.

Hardware matters for the absolute numbers; compare systems on the same host.

## What a point does

A run is the experiment's points (system × scenario × payload size × the system's variants), in a
seeded random order. Each point starts from nothing:

1. `docker compose down -v`, then MongoDB, Kafka, BaSyx and Mosquitto up (InfluxDB for influxdb-segment).
2. The system under test up (its Compose profile, `SUT_CPUS`/`SUT_MEMORY`).
3. **deploy**: the scenario is posted into the repository (the AIMC last); nodered-dmp's flow is
   generated and deployed, DataBridge's config files mounted. **ready**: the DMP reports the mapping
   `installed`; DataBridge and nodered-dmp pass a canary (a message with `seq` −1 published until its
   value is in the repository).
4. Northbound: tcpdump starts in the system's network namespace (O5); the open-loop load generator
   publishes the schedule (20 s warm-up, 60 s measured, 10 messages/s); the drain waits until the
   capture has been quiet for 5 s (at most `cooldown_s`).
5. The system stops, logs are saved, the testbed is removed, `residence.csv` is derived from the
   capture and the point is summarized.

A **southbound point** starts the device simulator before the system; once the system is ready a
canary is sent through the point's path until the device has it (a call: until its reply carries the
request back); a write through the repository has its change events observed on the point's transport
(O7); the client writes or calls on the schedule; the drain waits until the device is quiet. The DMP's
points multiply by their variant: a write's event transport (`event_transports`: `kafka`, `mqtt`, which
also switches BaSyx's events to that transport), a call's entry (`invoke_via`: `aas` through BaSyx, `dmp`
straight to the DMP's delegation endpoint, which separates BaSyx's share).

A failed point is recorded with its error and the run goes on.

## Measurement

| What | Tool | Sample |
| --- | --- | --- |
| load (northbound) | `tools/loadgen.py` | `sent.csv`: seq, phase, scheduled and actual send time; the PATCH reference also its round trip |
| O5 residence | tcpdump in the system's network namespace, `tools/residence.py` | `sut.pcap` (first 1500 bytes of each packet), `residence.csv`: per message, its last byte arriving, the system's request to the sink and the sink's answer reaching the system |
| client (southbound) | `tools/loadgen.py --format value`, `tools/invoke.py` | `sent.csv` as above; `calls.csv`: per call its send and reply time, status, whether the reply carried the request |
| O6 device (southbound) | `tools/device_sim.py` (MQTT, HTTP on 8090, OPC UA on 4840) | `device.csv`: per write or command, when the device had it whole |
| O7 change event (southbound) | `tools/observe_events.py` (Kafka or MQTT) | `events.csv`: when a consumer had the repository's event of each write |

The northbound message is `{"seq": n, "tSend": "<ns>", "value": "<n>|<ns>|xx…"}`, exactly the configured
size; the sink receives only its `value` member, which still names its message. `tSend` is a string:
nanoseconds since the epoch exceed 2^53. The figure's metric is `acked_ms`, from `tSend` to the sink's
answer to the write reaching the system: the same moment for the AAS repository and for InfluxDB, which
emits no BaSyx event. Nothing in the systems is instrumented.

All tools run in the harness image (`Dockerfile`) on the testbed network, so no measured message crosses
a published port; all timestamps come from the host's one clock. QoS is 1 everywhere and the broker's
queues are lifted, so a lost message is lost by the system under test.

`analysis/summarize.py` turns a point's raw samples into its `summary.json` (the measured phase only) and
can be re-run on any run folder; `analysis/figures.py` reads only the run's `summary.json`.

## Results

```
results/<experiment>/<UTC time>/
├── manifest.json          commit, harness digest, images, every system's image and commit, host, limits, config, plan
├── testbed.resolved.yml   the Compose project as it ran
├── summary.json           every point's summary
├── <figure>.pdf .png .csv the figure and the data it plots
└── points/<system>-<scenario>[-<variant>]-<size>B/
    ├── point.json  timeline.json  summary.json
    ├── samples/           raw samples (*.csv, sut.pcap)
    └── log/compose.log
```

`results/` is not versioned; publish the run folders behind the paper's figures with it.

`results/previous-harness/` holds the runs behind the figures currently in the paper, made with an
earlier version of this harness: one run per system, the DMP's two northbound scenarios in two runs,
the scenarios under former ids (S1-X, S1-XT, W1–W3, A1–A3), further observers running alongside. Delete
it once the paper's figures come from new runs.

## Scenarios

`../fixtures/scenarios.py` authors every scenario with aas-model (pinned by commit in
`../fixtures/pyproject.toml`) and writes `test_aas/<id>.json` and `test_aas/manifest.json`. The JSON is
generated, never edited; the runner refuses a scenario whose file does not match the manifest's SHA-256.

```bash
cd ../fixtures && uv run python -m scenarios
```

Each `<id>.json` is a plain AAS environment (one shell with its AID, AIMC and `Target` submodel), without
aas-pydantic's class markers. To inspect one, upload it to any BaSyx AAS environment, through the web UI
or `curl -F file=@test_aas/<id>.json http://<basyx>/upload`.

| ID | Mapping |
| --- | --- |
| `aas-property` | MQTT property `Device` (observable, QoS 1, declared JSON schema); the Source references the `value` member of its schema (`Device/properties/value`); Lua `return { Value = sources.Value }` → AAS Property `Target/Value` (xs:string) |
| `influxdb-segment` | the same message and Source into InfluxDB 2: the Sink is a TimeSeries LinkedSegment (`Target/Series/Segments/Live`, the DMP's InfluxDB target) whose Record has one string field `Value`; each message becomes one point |
| `write-mqtt` | AAS Property `Target/Setpoint` (xs:string; an event-sourced Source) → MQTT property `Setpoint` on `dmp-eval/write-mqtt/setpoint`, QoS 1; no Transformation |
| `write-http` | the same with an HTTP property, `PUT http://device-sim:8090/write-http/setpoint` |
| `write-opcua` | the same with an OPC UA String variable `ns=2;s=Setpoint` on `opc.tcp://device-sim:4840/`, written by Write |
| `invoke-mqtt` | AAS Operation `Target/Echo/operation` (input `Request`, output `Reply`), delegated by BaSyx to the DMP at its AAS API invoke path → MQTT 5 request/reply action `Echo` (`dmp-eval/invoke-mqtt/echo`, reply topic `…/reply`, QoS 1); request and response Lua copy the one value |
| `invoke-http` | the same with an HTTP action, `POST http://device-sim:8090/invoke-http/echo` |
| `invoke-opcua` | the same with the OPC UA Method `ns=2;s=Echo` of the Object `ns=2;s=Device` (arguments `Request`, `Reply`), invoked by Call |
